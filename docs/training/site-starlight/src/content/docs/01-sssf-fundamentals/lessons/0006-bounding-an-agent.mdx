## The roster

<p>A factory's agents are declared in one file, `adws/adw_sssf_config/sssf.config.yaml`. Each
agent is named — `planner`, `builder`, `reviewer` — never identified by its model. The name
is the identity; the model is a setting you can change under it. A roster entry sets the
model, thinking level, prompts, the tools it may call, and — the subject of this lesson —
what it may write.</p>

## Two controls that look alike and are not

<table>
  <tr><th></th><th>`tools`</th><th>`writes`</th></tr>
  <tr><td>Says</td><td>which tools the agent may call</td><td>which repo paths it may modify</td></tr>
  <tr><td>Checked</td><td>at call time, by the harness</td><td>after the phase, in code</td></tr>
  <tr><td>Can it protect a file?</td><td><strong>No</strong></td><td><strong>Yes</strong></td></tr>
</table>

<Callout kind="why" label="Why tools cannot protect a file">
<p>`bash` runs <em>anything</em> — including `git checkout adws/` — and `write` reaches any
  path. So an agent's tool list is a statement of <em>intent</em> that nothing enforces at the
  filesystem. The only control that actually bounds what an agent changes is `writes`, and it
  is enforced in `adw_modules/permissions.py` after every call.</p>
</Callout>

## What `writes` means

<table>
  <tr><th>`writes:` value</th><th>Means</th></tr>
  <tr><td>absent / `None`</td><td>unrestricted — may modify anything <em>except</em> `protected_files`</td></tr>
  <tr><td>`[]`</td><td>read-only with respect to the repo</td></tr>
  <tr><td>`["specs/", "mod.ts"]`</td><td>only these — a trailing `/` is a directory prefix, `*` a glob, else an exact path</td></tr>
</table>

<p>"Read-only with respect to the repo" is the careful phrase. A `writes: []` agent is not
mute: it still writes its own envelope, its plan, its findings into the session runtime under
`data_dir`. The scout and reviewer change nothing in the repo yet always record their work.</p>

## Protected files: the grader an agent cannot touch

<p>Some paths are off-limits to every agent that does not explicitly name them — the factory's
own machinery:</p>

```yaml
protected_files:
  - adws/adw_modules/        # the runner, gates, permissions themselves
  - adws/adw_sssf_config/    # the roster
  - adws/adw_*.py            # the chains
```

<Callout kind="trap" label="The builder is unrestricted — and still cannot edit its own grader">
<p>The `builder` has no `writes` key: it is the one agent allowed to change anything in the
  repo, because building is its job. And it <em>still</em> cannot touch `protected_files`. An
  agent that could edit `gates.py` or `quality.py` could make its own work pass by lowering
  the bar — so the thing that decides whether the work passed is exactly the thing the worker
  may not reach. "Naming a path in your own `writes` is what unlocks a protected one" — and no
  sane roster gives the builder `writes: [adws/adw_modules/]`.</p>
</Callout>

## How a breach is caught: change-sets, not surveillance

<p>Permissions are not enforced by watching each write as it happens. They are enforced by
<strong>comparing the repo before and after</strong> the agent ran:</p>

```python
def permitted(path, agent, cfg) -> bool:
    if is_session_runtime(path):                 # data_dir/ — always writable
        return True
    if any(_matches(path, p) for p in (agent.writes or [])):
        return True                              # naming a path unlocks it
    if any(_matches(path, p) for p in cfg.defaults.protected_files):
        return False
    return agent.writes is None                  # None = unrestricted, [] = read-only
```

<p>The change-set comes from `git diff HEAD --numstat` plus untracked files, snapshotted
before and after. Any path whose fingerprint changed is checked against `permitted`.</p>

<Callout kind="why" label="Why compare change-sets instead of intercepting writes">
<p>An agent that runs `git checkout adws/` does not <em>write</em> those files — it
  <em>discards</em> changes in them. A write-interceptor sees nothing; a change-set comparison
  sees the files are different afterward and flags them. This is not hypothetical: an agent
  once ran `git checkout adws/` and wiped work. Comparing states catches what watching writes
  cannot.</p>
</Callout>

## A breach is not a gate violation

<p>Keep the two failure classes separate. A <strong>gate violation</strong> is work an agent
can be <em>asked to fix</em> — the file it claimed does not exist, so it is corrected and tries
again (Lesson 5). A <strong>permissions breach</strong> is not a correction target: the agent
did something it was never allowed to do. It fails the run as a breach, not a fixable finding.</p>
