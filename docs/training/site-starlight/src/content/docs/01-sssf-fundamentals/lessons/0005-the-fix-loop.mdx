## The choice: restart or correct

<p>A gate fails. The agent's work is unacceptable. There are two ways to respond, and SSSF is
built entirely around choosing the second:</p>

<table>
  <tr><th></th><th>Restart</th><th>Correct</th></tr>
  <tr><td>What happens</td><td>throw the session away, start cold</td><td>re-prompt the <strong>same</strong> session</td></tr>
  <tr><td>The agent keeps</td><td>nothing — every lesson learned is gone</td><td>its full context window, intact</td></tr>
  <tr><td>Cost</td><td>the whole phase again</td><td>one message</td></tr>
  <tr><td>The prompt says</td><td>the original task, from scratch</td><td>exactly what was wrong, by name</td></tr>
</table>

<Callout kind="why" label="A correction costs one message; a restart costs everything">
<p>The coding agent treats its session id as create-or-continue, so "run an agent" and
  "continue an agent" are the same call. When JSON does not parse or a gate returns
  violations, <strong>nothing restarts</strong>. The harness sends one more message into the
  live session, naming the violations, and the context window stays intact. This is why the
  factory can be uncompromising about "done" without being ruinous about it.</p>
</Callout>

## The inner loop: gate corrections

<p>Inside a single agent phase, after the envelope parses, every attached gate runs. A
violation does not fail the phase — it re-prompts. Simplified from `agents.execute`:</p>

```python
for gate_attempt in range(1, phase.params.retries + 2):
    violations = [v for gate in call.gates
                    for v in gate(envelope, run).violations]
    if not violations:
        break                                   # green: done
    if gate_attempt > phase.params.retries:
        raise GateFailure(...)                   # budget spent: the phase fails
    correction = "Your previous response failed validation:\n- " + "\n- ".join(violations)
    result = send(correction)                    # SAME session, one more message
    envelope, _ = _parse_with_retries(run, phase, call, result, send)
```

<p>The number of corrections is `phase.params.retries` — the field you met on `PhaseParams`
in Lesson 4. `retries=0` means one shot, no corrections. `retries=1` means one correction
allowed. The loop is <strong>bounded by construction</strong>; it cannot run forever.</p>

### The note is the correction

<p>Recall from Lesson 2 that each gate check carries a `note`. On a failed check that note
becomes the violation text, and the violation text is what the agent is told. "Write notes
for the agent that must act on them" was not style advice — the note <em>is</em> the fix
instruction.</p>

## The outer loop: test, then fix

<p>The suite is a `code` phase (Lesson 4), so it cannot correct an agent by itself. The ADW
script wires the repair explicitly, bounded by a constant. From `adw_build_test.py`:</p>

```python
MAX_FIX_LOOPS = 3

for i in range(1, MAX_FIX_LOOPS + 1):
    with run.phase(PhaseParams(name=f"test_{i}", kind="code", owner="quality",
                               description="Run the suite and record pass/fail.")) as ph:
        test = quality.run_tests(run)
        record(ph, test)
    if test.passed:
        break
    with run.phase(PhaseParams(name=f"fix_{i}", kind="agent", owner="builder", retries=1,
                               description="Repair the code so the failing suite passes.")) as ph:
        ph.call(AgentCall(output_type=BuildOutput, prompt=fix_prompt,
                          previous=quality.as_envelope(test, "tests"),
                          gates=[gates.diff_matches_claims]))

return run.finish(accepted=test.passed,
                  reason=f"the suite still failed after {MAX_FIX_LOOPS} fix attempt(s)")
```

<Callout kind="why" label="The failing suite arrives as an envelope">
<p>Look at `previous=quality.as_envelope(test, "tests")`. The test result is wrapped into an
  <strong>envelope</strong> — the same typed object an agent produces — and handed to the
  builder as its `previous`. "Testing is code" and "context crosses as an envelope" are not
  two systems bolted together: the suite's failure comes through the <em>same door</em> an
  agent's report does, so the repair loop needs no special case. Lessons 2, 3, and 5 are one
  mechanism seen three times.</p>
</Callout>

## Two surfaces, one machine

<p>Both kinds of failure feed the same correction machinery:</p>

<table>
  <tr><th>Failure</th><th>Detected by</th><th>Bounded by</th><th>Correction carries</th></tr>
  <tr><td>claim gate violation</td><td>`agents.execute`, inner loop</td><td>`retries`</td><td>the gate's `note`</td></tr>
  <tr><td>suite failed</td><td>a `code` test phase</td><td>`MAX_FIX_LOOPS`</td><td>the failing output, as an envelope</td></tr>
</table>

<Callout kind="trap" label="A dead gate disables the whole machine">
<p>The fix loop only fires on a <strong>failure</strong>. So when the test gate is an
  `echo` that exits 0 (Lesson 1), there is no failure to feed it. The builder writes broken
  code, the gate says PASSED, the loop never runs, the correction is never sent, and the
  commit phase lands the bug — while the trace reads 5/5 success.</p>
<p><strong>A dead gate does not merely fail to catch bugs. It disables the repair machinery
  and then certifies the result.</strong> This is why Lesson 1 insisted a gate be
  <em>watched failing</em>: an unverified gate is not a weak safety net, it is a switched-off
  one wired to a green light.</p>
</Callout>
