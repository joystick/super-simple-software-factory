<p>You can look at any run's `envelope.json` and say exactly what one phase told the next —

  check fail.</p>
</Callout>

## The seam problem

<p>A factory run is a chain of phases: a planner writes a spec, a builder implements it, a
reviewer judges it. Each is a <em>separate</em> agent call — a fresh context. So how does
the builder learn what the planner decided?</p>

<p>The tempting answer is "they share a conversation." SSSF refuses it. The planner's chat
transcript never reaches the builder. Exactly one thing crosses the seam: a typed JSON
object called the <strong>envelope</strong>.</p>

<Callout kind="why" label="Context transfers in code, not in conversation">
<p>An agent has exactly two output channels: reference files it writes into
  `context_handoff/`, and one final valid-JSON response parsed against the output type its
  call declared. Code persists that response as `envelope.json`, records it in the trace,
  and injects it into the next agent's prompt.</p>
<p>The seam is owned by code, not by the model. That is "agent proposes, code disposes"
  applied to <strong>the hand-off</strong> — the same move Lesson 1 made for the verdict.</p>
</Callout>

## A real hand-off

<p>Here is an actual planner envelope from a real run (session `b16c5c29`), verbatim but for
trimming the long `notes_for_next_agent`. The task was to add a `CouponDiscount` rule to the
pricing engine:</p>

```json
{
  "agent_name": "planner",
  "output_type": "PlanOutput",
  "status": "success",
  "summary": "Plan to add a CouponDiscount rule to app/pricing.py with a coupon_code parameter on price_cart, extending existing rules with **_kwargs for forward compatibility, plus four tests in tests/test_pricing.py.",
  "artifacts": [
    "adws/adw_data/sessions/b16c5c29/context_handoff/plan.md",
    "specs/b16c5c29_coupon-discount.md"
  ],
  "notes_for_next_agent": "The plan requires changes to two files only: app/pricing.py and tests/test_pricing.py. Key points: (1) Add **_kwargs to MemberDiscount.apply and BulkDiscount.apply so they accept-and-ignore the new coupon_code keyword. (2) Insert the CouponDiscount class after BulkDiscount. (3) Add coupon_code to price_cart's keyword-only params and pass it through. (4) Add four new tests. Run pytest to verify.",
  "commit_message": "Add spec for coupon discount support in the pricing engine"
}
```

<p>Everything the builder needs is here, and nothing else is. The planner's reasoning, its
false starts, the messages it took to get here — none of that crosses. The builder is
handed `notes_for_next_agent` and pointed at the `artifacts`. That is the whole context
transfer.</p>

<p>The builder's own envelope, from the same chain, closes the loop by <em>reporting</em>
what it did:</p>

```json
{
  "agent_name": "builder",
  "output_type": "BuildOutput",
  "status": "success",
  "summary": "Added CouponDiscount rule with code-matching logic to the pricing engine, updated price_cart to accept coupon_code, added **_kwargs to existing rules for forward compatibility, and added four tests covering match, mismatch, no code, and invalid percent.",
  "changed_files": ["app/pricing.py", "tests/test_pricing.py"],
  "notes_for_next_agent": "Run `.venv/bin/python -m pytest tests/test_pricing.py -v` to verify all 32 tests pass. The CouponDiscount class is in app/pricing.py after BulkDiscount.",
  "commit_message": "Add CouponDiscount rule and coupon_code support to price_cart"
}
```

## The typed shape

<p>Every envelope extends one base. The base is deliberately tiny:</p>

```python
class EnvelopeBase(BaseModel):
    status: Literal["success", "fail"]
    summary: str = ""
    artifacts: list[str] = []           # files this phase produced
    notes_for_next_agent: str = ""      # the hand-off, in prose
```

<p>Each phase declares a subtype that adds only what <em>that</em> phase is accountable for:</p>

<table>
  <tr><th>Output type</th><th>Adds</th><th>Why that field</th></tr>
  <tr><td>`PlanOutput`</td><td>`commit_message`</td><td>the spec file it wrote is committed on its own</td></tr>
  <tr><td>`BuildOutput`</td><td>`changed_files`</td><td>the exact files the diff should contain</td></tr>
  <tr><td>`ReviewOutput`</td><td>`approved`, `findings`, `blocking`</td><td>a verdict with its evidence</td></tr>
  <tr><td>`ScoutOutput`</td><td>`findings`</td><td>read-only recon, one note per file</td></tr>
</table>

<p>The `output_type` on the call is a contract. If the agent's final message does not parse
into that type — a missing field, a wrong shape, not even JSON — the response is rejected.</p>

<Callout kind="why" label="A rejected envelope is a correction, not a restart">
<p>When the JSON does not parse to the declared type, <strong>nothing restarts</strong>. The
  harness re-prompts the <em>same</em> session naming exactly what was wrong, and the
  context window stays intact. A cold restart throws away everything the agent learned; a
  correction costs one message.</p>
<p>This is the same fix-loop machinery Lesson 2's envelope gates feed. The envelope is what
  they feed it <em>with</em>.</p>
</Callout>

## Why gates read the envelope, not the agent

<p>Recall from Lesson 2: an envelope gate has the signature `gate(envelope, run) ->
GateReport`. Now you can see what it is handed. Nobody knows which files an agent will
touch before it finishes, so gates run <strong>after</strong> the fact against the
envelope's own declarations:</p>

```python
def diff_matches_claims(envelope, run) -> GateReport:
    report = GateReport()
    for f in envelope.changed_files:        # the builder's own claim
        p = Path(f)
        report.check(f, p.exists(),
                     "in the diff" if p.exists()
                     else "claimed changed but not on disk")
    return report
```

<p>The builder <em>said</em> it changed `app/pricing.py`. `diff_matches_claims` reads that
claim straight out of the envelope and checks it against reality. `artifacts_exist` does the
same for the planner's `artifacts`. The envelope is the surface every claim gate stands on.</p>

<Callout kind="trap" label="An envelope is a set of claims, not a set of facts">
<p>Producing this JSON requires none of it to be true. `status: "success"` is a string the
  agent chose. `notes_for_next_agent` can describe a file that was never written.
  `changed_files` can name a file the diff does not contain.</p>
<p>Gates check the <strong>mechanically checkable</strong> part — did the file appear, is it
  non-empty, is the claimed change on disk. Whether the plan is any <em>good</em> is a
  reviewer's job. And whether a gate that reads a claim can actually fail is <strong>your</strong>
  job to verify — the Lesson 1 ritual, one level up.</p>
</Callout>
