## Two steps to a factory

<p>The whole system is a <strong>skill</strong> you stamp into any repo. The skill is the
product; everything else — the `adws/`, the `justfile`, the demo app — is stamped output.</p>

```bash
# 1. get the skill into your repo (it lives under .claude/skills/sssf/)
# 2. stamp the factory
uv run .claude/skills/sssf/scripts/install.py
```

<p>Stamping writes a starter `adws/` tree, a `sssf.config.yaml` roster, the twelve chains, and
a `justfile` wrapping them — so a fresh repo gets `just sessions`, `just phases`, `just plan`,
`just sdlc` out of the box.</p>

## What you must change before you trust it

<Callout kind="trap" label="A freshly stamped factory certifies everything">
<p>The shipped quality blocks are <strong>placeholders that exit 0</strong>. Straight after
  stamping, your test phase is theatre: it passes on any code, and — because a passing gate
  never fires the fix loop (Lesson 5) — it will commit a bug and certify the run 5/5. Stamping
  gives you the <em>shape</em> of a factory, never its substance. The substance is the wiring
  you do next, each piece <em>watched failing</em>.</p>
</Callout>

## The capstone rep: certify a bug, then catch it

<p>This is the single most convincing exercise in the course. Do it once and the whole
philosophy is no longer something you were told.</p>

<p><em>All three reps are <strong>[run]</strong> — they drive the
<a href="/01-sssf-fundamentals/reference/0004-wiring-your-factory/">wired factory</a>, and the
first one costs about a dollar. It is worth it.</em></p>

<ol class="steps">
  <li>
    <p><strong>[run]</strong> <strong>Watch it certify a bug.</strong> In a throwaway copy of a real repo (e.g.
    the TypeScript rebuild repo), leave the test block as the shipped placeholder. Run `just sdlc` on a task
    that introduces a real bug. Watch the factory build it, "test" it green, review it, commit
    it, and write `status: success · phases 5/5`. Read the trace: every row is true, and the
    result is wrong. (Costs roughly $0.60–£1 — the most useful dollar in this course.)</p>
  </li>
  <li>
    <p><strong>[run]</strong> <strong>Wire the gate — and watch it fail.</strong> Point the test block at the real
    suite. Introduce the bug's class deliberately and confirm the gate goes red and the others
    stay green (Lesson 1's procedure). Only now is it a gate.</p>
  </li>
  <li>
    <p><strong>[run]</strong> <strong>Re-run and watch it catch.</strong> Run `just sdlc` again on the same task. This
    time the failing suite fires the fix loop, the builder is corrected in place, and the run
    either recovers or fails honestly with a named reason. Same factory, same prompt — the only
    difference is a gate you watched fail.</p>
  </li>
</ol>

## Reviewing like an operator

<p>A finished run is not a finished job. Read the diff — the code, not the summary. Check the
cost against what the work was worth. And trust the gates <em>only</em> because you verified
them, never because the banner is green. "A factory is exactly as trustworthy as its weakest
gate, and a gate's trustworthiness cannot be read, only demonstrated" — the first sentence of
the course, now something you have done rather than read.</p>
