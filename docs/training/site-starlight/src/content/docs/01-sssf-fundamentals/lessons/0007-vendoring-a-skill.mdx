<Callout kind="win" label="The win">
<p>You can explain why an SSSF agent cannot see the skills installed on your machine, carry
  one in on purpose with `skill_engineering`, and say — precisely — what that does and does not
  change about the run. You will know why it is a list of paths, not a single named skill, why
  composition order is not alphabetical, and why the gates still do all the checking.</p>
</Callout>

## The gap this closes

<p>Every lesson so far has been about a run's own machinery: phases, gates, the fix loop,
`writes`. None of it touches a different fact — the interactive skills you use every day
(`/tdd`, `/codebase-design`, whatever is installed on your machine) are invisible to a headless
SSSF agent. It runs with `--setting-sources ''`, so it starts with none of your skill
directory. Grep the agent launch args in `adws/adw_modules/` to confirm on your version. That
gap does not close by installing more skills locally — it closes only for a skill you name,
on purpose, per agent.</p>

## A list of paths, not a switch

<p>`skill_engineering` is a roster field, set per agent (or in `defaults`, inherited by every
agent that does not override it):</p>

```yaml
agents:
  builder:
    coding_agent: claude_code
    skill_engineering:
      - adws/adw_data/skill_engineering/tdd/SKILL.md
      - adws/adw_data/skill_engineering/codebase-design/SKILL.md
```

<p>It is a **list**, because an agent's protocol needs are not one-size. A builder might carry
`tdd`; a refactor-only agent might carry `codebase-design` alone, or both. Each entry is a file
path — there is no registry lookup, no name resolution. If the path is wrong, `agents.validate()`
raises before any agent spawns; a typo in the roster is a config error, not a wasted turn.</p>

<Callout kind="trap" label="claude_code only">
<p>`skill_engineering_applies(agent)` is `agent.coding_agent == "claude_code"` — nothing else.
Set the field on a `pi` or `agy` agent and it is silently ignored at compose time, though
`agents.validate()` does warn: "skill_engineering is set but coding_agent is ... and will be
ignored." Read that warning; it is the whole difference between a config that does something
and one that only looks like it does.</p>
</Callout>

## Vendor, then attach

<p>Two separate, deliberate acts — never one auto-updating link:</p>

```bash
uv run <sssf>/scripts/vendor_skill.py ~/.claude/skills/tdd/SKILL.md
# writes adws/adw_data/skill_engineering/tdd/SKILL.md, stamped with provenance
```

<p>The vendored copy opens with an HTML-comment header — `source`, `date`, a `sha256` of the
original — invisible in a rendered Markdown viewer and stripped before the text ever reaches a
model. It exists so drift from the source skill is detectable later: `vendor_skill.py --check`
re-hashes and tells you if your copy has fallen behind. Vendoring produces a diff you commit,
not a symlink that changes under you.</p>

<p>Attach it by adding the path to an agent's `skill_engineering` list, as above. Nothing else
is required — no separate "enable" flag.</p>

## What actually happens to the prompt

<p>At call time, `skill_engineering.compose()` builds the final system prompt:</p>

```python
def compose(system_text: str, skill_paths: list[str]) -> str:
    parts = [system_text]
    for raw_path in skill_paths:
        name, body = _read(raw_path)          # provenance header stripped here
        parts.append(DELIMITER.format(name=name) + body)
    return "".join(parts)
```

<p>The agent's own system prompt always comes first — its identity and output contract outrank
any borrowed protocol — then each skill's text, **in the order you listed them**, never sorted.
Composition order is the engineer's, not alphabetical: a stable order matters for prompt
caching, and sorting would silently change which instruction a model reads first.</p>

## Cost is visible, and it is only a warning

<p>Vendored text is real tokens on every call that agent makes. `estimate_tokens()` gives a
rough, model-agnostic count — never presented as a billed figure — and `just sessions` reports
it per run. An agent can carry a soft `skill_token_budget`; going over it produces a console
warning, not a blocked run. This is a **soft ceiling you watch**, the same posture as
everything else in this course: nothing stops the agent from running over-budget, the same way
nothing stops a placeholder gate from reporting green. You are the one who reads the number.</p>

## The gates still decide, not the skill

<Callout kind="why" label="Why this doesn't need a new kind of gate">
<p>`skill_engineering.py`'s own module docstring says it plainly: this changes how the agent
works, never what is checked afterward. Attaching `tdd` puts red-green-refactor language in the
builder's prompt. Nothing verifies the agent actually wrote a failing test first — the outcome
gates (Lesson 1) still judge the diff and the test run, exactly as before. A skill is an
instruction you handed the agent, not a promise it kept. If you want evidence it worked
test-first, that evidence has to come from the same place all your other evidence comes from: a
gate that watched something fail, then pass.</p>
</Callout>
