<Callout kind="win" label="The win">
<p>You can open `sssf.db` after any run and answer, precisely: which phases ran, in which
  lanes, at what cost, with how many correction attempts, and what each gate actually checked.
  And you can name — out loud — the one question the trace is structurally unable to answer.</p>
</Callout>

## One data path

<p>Everything a run does streams into a single SQLite database as it happens. There is no
second channel and no end-of-run batch:</p>

<Callout kind="why" label="Agents write to SQLite; readers poll SQLite">
<p>The tracer tails the coding agent's JSONL output line by line and inserts each event
  <em>while the agent is still working</em>, so a tool call is visible mid-run, not after.
  The database is WAL, so a reader never blocks a running workflow. "What is happening right
  now" and "what happened last week" are the same query against the same tables.</p>
</Callout>

## Seven tables

<table>
  <tr><th>Table</th><th>One row per…</th></tr>
  <tr><td>`sessions`</td><td>a run — its request, status, total tokens and cost</td></tr>
  <tr><td>`phases`</td><td>a phase — name, kind, owner, status, attempt</td></tr>
  <tr><td>`events`</td><td>anything that happened — phase_start, tool_call, gate_pass/fail, error</td></tr>
  <tr><td>`envelopes`</td><td>a hand-off — the typed payload, whether it was valid, which attempt</td></tr>
  <tr><td>`gate_results`</td><td>a gate run — passed, violations, and the checks behind them</td></tr>
  <tr><td>`agent_sessions`</td><td>an agent in a run — its session id and context-window occupancy</td></tr>
  <tr><td>`processes`</td><td>a live pid — so a stuck run can be found and stopped</td></tr>
</table>

## The four recipes you will actually use

<p>A stamped repo ships these `just` recipes; each is one line of SQL:</p>

```sql
-- just sessions        the last runs, newest first
select adw_id, status, substr(request,1,50), total_tokens, round(total_cost,4)
  from sessions order by started_at desc limit 10;

-- just phases <adw_id>   the spine of one run
select seq, name, kind, owner, status, attempt
  from phases where adw_id = ? order by seq;

-- just tail <adw_id>     the most recent events (live during a run)
select rowid, type, name, started_at
  from events where adw_id = ? order by rowid desc limit 25;

-- just procs <adw_id>    what is still alive
select kind, name, pid, command from processes
  where adw_id = ? and ended_at is null;
```

<p>`phases` is the one you will read most: it is Lesson 4's spine, made queryable. The
`attempt` column is Lesson 5's fix loop, counted.</p>

## A green gate says what it checked

<p>The `gate_results` table has a `checks_json` column — `[{item, ok, note}]`, the
individual checks behind the verdict, not just pass/fail. This is Lesson 1 and 2 written into
the schema. A gate that passed tells you <em>what</em> it verified:</p>

```
gate: artifacts_exist   passed: 1
checks: [
  {item: "specs/b16c5c29_coupon-discount.md", ok: true, note: "exists, 2.1KB"},
  {item: ".../context_handoff/plan.md",        ok: true, note: "exists, 4.4KB"}
]
```

## What the trace cannot tell you

<Callout kind="trap" label="A faithful trace of a dead gate is indistinguishable from a faithful trace of a live one">
<p>The database records, perfectly, that a gate ran, that it passed, and which items it
  examined. It cannot record whether that gate was <em>able to fail</em>. Run the factory with
  a real, verified test gate and it writes `status: success, 5/5`. Run it with an `echo` gate
  on broken code and it writes the <em>same</em> `status: success, 5/5` — both entries true,
  both faithful, one meaningless.</p>
<p>The trace answers "what ran and what did it cost." It cannot answer "did any of it mean
  anything." That question was settled earlier or not at all — by watching the gate fail
  (Lesson 1). Coverage of the record is not coverage of reality.</p>
</Callout>

## Read this next

<p><strong>Primary source:</strong> the `CREATE TABLE` block at the top of
`adws/adw_modules/tracer.py` in `sssf-play` — the whole schema in one screen. Then the
`sessions`, `phases`, `tail`, and `procs` recipes in the `justfile`, which are just SQL you

<p>For the wider idea, revisit <a href="https://martinfowler.com/bliki/TestCoverage.html">Fowler
on test coverage</a>: a coverage report says which lines ran, never whether the assertions
around them meant anything. The trace has exactly that shape, one level up.</p>
