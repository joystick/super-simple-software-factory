<Callout kind="win" label="The win">
<p>You can look at any factory — yours or a colleague's — and say precisely what its
  green banner does and does not establish. And you can settle the question in about three
  minutes per gate.</p>
</Callout>

## What a gate is

<p>A <strong>gate</strong> is a deterministic check that decides whether an agent's work is
acceptable. Three properties, and none of them is clever:</p>

<ol>
  <li><strong>Code runs it, not a model.</strong> No LLM is asked "did the tests pass?" A
  subprocess runs a command and reads the exit code.</li>
  <li><strong>It judges the result, not the claim.</strong> The agent says "I added the
  feature and tests pass." The gate ignores that sentence and runs the suite.</li>
  <li><strong>Its verdict is an exit code.</strong> `0` passes. Anything else
  fails.</li>
</ol>

<p>That is the entire mechanism. The lack of cleverness is the point: a verdict you cannot
argue with.</p>

## The problem

<p>A gate's substance is <em>the command it runs</em>. And:</p>


```
echo "PLACEHOLDER"   →  exit 0
deno test            →  exit 0     (when the suite genuinely passes)
```


<Callout kind="why" label="The core idea, and everything else follows from it">
<p>A gate has two states that are <strong>identical from the outside</strong>: it checked
  something and found nothing wrong, or it is incapable of finding anything wrong.</p>
  <p>A green result does not distinguish them. Neither does the trace. Neither does
  reading the config, as we will see.</p>
</Callout>

<p>Executed on a repo containing one file and no tooling whatsoever:</p>


```
$ uv run adws/adw_quality.py "is this repo healthy?"

  quality test:      passed (exit 0)   ← ran: echo 'PLACEHOLDER test…'
  quality lint:      passed (exit 0)   ← ran: echo 'PLACEHOLDER lint…'
  quality typecheck: passed (exit 0)   ← ran: echo 'PLACEHOLDER typecheck…'
  quality build:     passed (exit 0)   ← ran: echo 'PLACEHOLDER build…'
  checks: 4/4        status ✓ success
```


<p>No test suite. No linter. No typechecker. Four `echo` statements and a green
banner.</p>

## Reading the command is not enough either

<p>The obvious defence is to inspect what each gate runs. Necessary, and insufficient —
a real tool with a real command can also check nothing:</p>


```
$ deno test --filter "smoke"
ok | 0 passed | 0 failed | 66 filtered out     exit 0

$ deno test
ok | 66 passed | 0 failed                      exit 0
```


<p>No placeholder anywhere. A real runner, a plausible command, exit 0, <strong>zero tests
executed</strong>. A filter that matches nothing, a path that points at the wrong
directory, a suite scoped to a folder someone renamed — each produces this.</p>

## The only thing that settles it

<p>For <strong>each</strong> gate `G`, separately:</p>

<ol class="steps">
  <li><p>Introduce a defect <strong>of the class that tool exists to catch</strong>.</p></li>
  <li><p>Run every gate.</p></li>
  <li><p>Require <em>both</em>: `G` goes red, <strong>and every other gate stays
  green</strong>.</p></li>
  <li><p>Restore.</p></li>
</ol>

<p>The second half of step 3 is the half people drop, and it is the half that isolates.
Red-on-`G` alone cannot distinguish "lint caught my unused import" from
"everything is red because I broke the build".</p>

### Choosing the probe

<p>A probe aimed at the wrong tool produces a <em>false diagnosis</em> — the gate stays
green, and you conclude it is broken when it is healthy. Measured:</p>

<table>
  <tr><th>Probe</th><th>pytest</th><th>ruff</th><th>mypy</th></tr>
  <tr><td>extra spaces around operators</td><td>PASS</td><td>PASS</td><td>PASS</td></tr>
  <tr><td>unused import</td><td>PASS</td><td><strong>FAIL</strong></td><td>PASS</td></tr>
  <tr><td>wrong type annotation</td><td>PASS</td><td>PASS</td><td><strong>FAIL</strong></td></tr>
</table>

<p>Whitespace is a <em>formatter's</em> job, not a linter's — which is also why formatting
must never be a gate at all. It is auto-fixable, so gating on it turns a fix into a
failure.</p>

<table>
  <tr><th>Tool</th><th>Job</th><th>Probe with</th></tr>
  <tr><td>formatter</td><td>layout</td><td><em>nothing — not a gate</em></td></tr>
  <tr><td>linter</td><td>dead code, suspicious patterns</td><td>an unused import</td></tr>
  <tr><td>type checker</td><td>types</td><td>a wrong annotation</td></tr>
  <tr><td>tests</td><td>wrong behaviour</td><td>change a value an assertion depends on</td></tr>
</table>

### Reading the result

<table>
  <tr><th>Outcome</th><th>Diagnosis</th></tr>
  <tr><td>`G` stays <strong>green</strong></td><td>The gate does not reach that defect. Fix the gate — or if `G` is a test suite, suspect the <strong>test</strong>.</td></tr>
  <tr><td>Everything goes red</td><td>The probe was not specific. Choose a narrower one.</td></tr>
  <tr><td>One <em>other</em> gate also goes red</td><td>A real overlap, or the wrong probe. Overlaps exist — `deno test` type-checks, so a type error trips both `test` and `check`. Know your overlaps; do not accept surprises.</td></tr>
</table>

## Why per gate, and not "the build went red"

<p>A dead lint gate and a real bug, run together:</p>


```
bug present   test: failed   lint: passed   typecheck: passed   →  2/3  RED
bug fixed     test: passed   lint: passed   typecheck: passed   →  3/3  GREEN
```


<p>The build went red. A team that stops there concludes all three gates work. One is an
`echo`. Once the bug is fixed, that dead gate is <strong>indistinguishable</strong>
from a healthy one.</p>

<p>Breaking one thing proves <em>at least one</em> gate noticed. It never says which, and
says nothing about the others.</p>

<Callout kind="trap" label="A dead gate is worse than no gate">
<p>SSSF's fix loop hands a failing gate's verbatim output back to the builder to repair,
  then re-runs the gate. So when the test gate is an `echo`:</p>
  
```
build    the builder writes broken code
test     echo → exit 0 → PASSED
         ↓  the fix loop NEVER FIRES — there is no failure to feed it,
            and the builder is never told anything is wrong
commit   "land the code only after the suite came back green" — it did
trace    status ✓ success · phases 5/5 passed
```

  <p>The bug is committed and the permanent record says the run succeeded. Nobody lied;
  every component did its job correctly. <strong>A dead gate does not merely fail to catch
  bugs — it disables the repair machinery and then certifies the result.</strong></p>
</Callout>

## What SSSF actually gives you

<Callout kind="why" label="One sentence">
<p>SSSF guarantees that an agent's <strong>claims</strong> are replaced by a
  <strong>deterministic verdict</strong> before work proceeds. Agent proposes, code
  disposes.</p>
  <p>Everything else — roster, envelopes, trace, fix loop, permissions — serves that one
  guarantee. Its entire strength is the gates. <strong>A factory is exactly as trustworthy
  as its weakest gate, and a gate's trustworthiness cannot be read, only
  demonstrated.</strong></p>
</Callout>
