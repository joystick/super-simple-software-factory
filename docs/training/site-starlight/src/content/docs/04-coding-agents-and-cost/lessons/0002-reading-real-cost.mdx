<p>`just sessions` already surfaces `total_tokens` and `total_cost` per run — this lesson is about reading those numbers honestly rather than mechanically: what a cost figure does and doesn't tell you (it says what a run cost, not whether the result was worth it), why costs from someone else's repo never transfer to yours, and how to measure your own factory's real cost on a throwaway branch before budgeting against it for real.</p>

<Callout kind="win" label="The win">
<p>You can trace a `total_cost` figure from the `sessions` row back through `agent_end`
  events to the driver that produced it, say which of the four components it is made of, tell
  spend apart from context occupancy on sight, recognize a `$0.00` that means <em>unknown</em>
  rather than <em>free</em>, and explain why the only cost baseline worth budgeting against is one
  you measured on your own repo.</p>
</Callout>

## Where the two numbers come from

<p>`just sessions` is a one-line SQL query against the trace database:</p>

```
select adw_id, status, substr(request,1,50), total_tokens, round(total_cost,4)
from sessions order by started_at desc limit 10;
```

<p>Those two columns are accumulated, never computed after the fact. Every `send()` inside
`agents.execute()` calls `run.add_usage(result.tokens, result.cost)`, and the tracer applies it
as `UPDATE sessions SET total_tokens=total_tokens+?, total_cost=total_cost+? WHERE adw_id=?`.
So the session row is the sum of every driver call the run made — first prompts, malformed-JSON
retries, gate corrections, fix-loop iterations — across every agent phase. A phase that retried
three times is in there three times.</p>

<p>Where the driver gets each number depends on the CLI behind it. Under `claude_code`, the
terminal `result` event of a `claude -p` turn carries `total_cost_usd` and a `usage` block, and
`agent_cc.run()` reads both from there — that event is "the run's billed usage — CUMULATIVE over
every internal turn (13 model calls in a routine scout run)." Under `pi`, each assistant
`message_end` carries `usage.cost.total`, and `agent_pi.run()` sums them. Either way the result
lands in the same two `PiResult` fields, `tokens` and `cost`, plus a per-component
`UsageBreakdown`.</p>

## The breakdown: four components, one nested share

<p>`UsageBreakdown` in `data_types.py` "mirrors pi's `usage` shape one-for-one so the numbers
reconcile with what pi itself reports":</p>

<table>
  <tr><th>Field</th><th>What it counts</th></tr>
  <tr><td>`input_tokens`</td><td>Prompt tokens sent at the full input rate — <strong>excludes</strong> cache reads</td></tr>
  <tr><td>`output_tokens`</td><td>Tokens the model wrote, including its thinking</td></tr>
  <tr><td>`cache_read_tokens`</td><td>Prompt tokens served from cache, billed at the cheaper cache-read rate</td></tr>
  <tr><td>`cache_write_tokens`</td><td>Prompt tokens written into cache this turn</td></tr>
  <tr><td>`reasoning_tokens`</td><td>The thinking <em>share</em> of `output_tokens` — nested, not a fifth component</td></tr>
  <tr><td>`total_tokens`</td><td>The four components above, summed</td></tr>
  <tr><td>`*_cost`, `total_cost`</td><td>Dollars per component, and their sum</td></tr>
</table>

<p>Two reading rules fall out of that shape. First, `input_tokens` alone understates the prompt:
"add them to learn the size of the prompt that was sent" — meaning `input + cache_read` is the
real prompt size, and a run with a large `cache_read_tokens` figure is one whose stable system
prompt (including any vendored `skill_engineering` text) was being served cheaply. Second,
`reasoning_tokens` is inside `output_tokens`: "measured across every session on disk, reasoning
is always ≤ output and the four components above always sum to `totalTokens`." Adding it to the
total double-counts.</p>

<p>The per-phase view lives on the `agent_end` event, whose payload carries `cost`, `usage`
(this breakdown), `context_tokens`, and `context_window`. The observability reference notes it
is "summed across every send the phase made, so a phase that retried on a bad envelope or a
failed gate shows what all its attempts cost, not just the last one." That is the number to look
at when one phase is eating the budget — `just sessions` only tells you the run total.</p>

## Spend is not occupancy

<Callout kind="trap" label="total_tokens only ever grows; the context window does not">
<p>`sessions.total_tokens` and `events.tokens` bill every turn, so they accumulate. `context_tokens`
  on the `agent_sessions` row is a different quantity: "how full the window actually was when the
  agent stopped," measured against `context_window`. The observability reference's own example:
  "an agent that burned 100k tokens may be sitting in a 15k window." `agent_cc.py` learned this the
  hard way — reading the cumulative `result` usage as occupancy "reports 298k against a 200k
  window," which is why occupancy is read from the per-message assistant usage instead. When you
  read a big `total_tokens`, you are reading a bill, not a context-pressure warning.</p>
</Callout>

## When $0.00 means unknown

<p>A zero in the cost column is only trustworthy if the driver behind it reports dollars at all.
From the config reference: `agy` "reports tokens but never dollars, so `PiResult.cost` stays 0.00
for this interface. A `$0.00` in the trace means <em>unknown</em>, not <em>free</em>." `opencode`,
by contrast, carries a numeric `cost` on each `step_finish` event and sums it — "the one place
`opencode` is stronger than its closest sibling interface." Before comparing two runs by cost,
check the `coding_agent` column on their `agent_sessions` rows; a `$0.00` `agy` run has not
beaten a `$4.42` `claude_code` run on price, it has simply declined to say.</p>

<p>Under `claude_code` there is a second thing the dollar figure is quiet about: whose bill it
is. The previous lesson covered `API_AUTH_VARS` stripping — agents run on the logged-in Claude
Code session, never on a metered API key. `total_cost_usd` is what the CLI reports the turn
would cost at API rates; it is the right number for comparing runs, and it is not necessarily an
invoice.</p>

## What a cost figure does not tell you

<p>The adoption playbook's "Read what happened" step is the honest frame: "check cost per run
early and often, and build your own baseline from those numbers — no figure from someone else's
repo transfers to yours." Its list of things not to assume names the reason: "Language, suite
size, and repo shape dominate. Measure your own on a throwaway branch before budgeting." The
playbook's own history is instructive here — its v2.0 and v2.1 changelog rows record that it
<em>removed</em> the last cost figures it used to quote "so the measure-it-yourself stance is
consistent."</p>

<Callout kind="why" label="Cost is a fact about the run, not a verdict on it">
<p>`total_cost` says what a run spent. It says nothing about whether the diff is any good, whether
  the reviewer's `approved: true` was earned, or whether a cheaper model would have produced the
  same spec. The playbook's instruction when one agent dominates spend is not "switch to the cheap
  model" — it is "try a cheaper model on it and compare both the price <em>and</em> the output it
  produces. Do not assume the expensive model plans better; run the same prompt through both on
  your own repo and read the two specs." A cost number is one input to that comparison. Reading
  it as the answer skips the part where you read the diff.</p>
</Callout>

<p>The one cost figure the playbook does still carry is deliberately framed as evidence for a
specific claim, not a benchmark: the first live end-to-end dark-factory dispatch cost "$4.42,
4.3M tokens" for ten passed phases and a reviewer-approved change on one particular repo. That
number tells you the loop ran and what <em>that</em> run cost. It does not tell you what yours
will.</p>

## How to build your own baseline

<ol class="steps">
  <li>Cut a throwaway branch on your real repo — not a sample project. Repo shape is what
  dominates cost.</li>
  <li>Run a representative prompt through `just sdlc` two or three times. Repeated runs matter:
  a single figure hides retry variance.</li>
  <li>Read `just sessions` for the run totals, then `just phases <adw_id>` and the `agent_end`
  payloads to see which phase and which component (input vs cache-read vs output) carries the
  spend.</li>
  <li>If `skill_engineering` is set on any agent, remember the config reference's note that skill
  text "is billed on every internal turn of a phase." Set `skill_token_budget` so you are warned —
  never failed — when a composed prompt exceeds what you expected to pay for it.</li>
  <li>If one agent dominates, change its `model:` and re-run the same prompt. Compare the two
  `total_cost` figures <em>and</em> the two outputs before deciding.</li>
  <li>Budget against what you measured. Throw the branch away.</li>
</ol>
