<Callout kind="win" label="The win">
<p>You can explain why `just watch` never judges a ticket itself and why that is the same
  decision Chapter 6 already made about the headless interview; you can name what `/triage`
  actually checks before it writes `ready-for-agent`; and, after running `/to-spec` or

  edit before you commit.</p>

<p>`just watch` only ever picks up issues already at `ready-for-agent` — every judgment about whether a ticket is feasible, compatible with what's already live, and compliant happens upstream of that label, interactively, inside `/triage`. This lesson covers why that judgment call stays a human's on purpose (an unattended loop making its own security/compliance calls has no one to catch it when it's wrong, the same failure shape Part C's headless-interview problem already fixed once), and the sharp edge where running `/to-spec` or `/to-tickets` interactively self-promotes a ticket past this gate by default — and what to check for before committing when that happens.</p>

## What the watcher refuses to decide

<p>The obvious design is for `just watch` to read a raw issue, weigh it against `CLAUDE.md`,
`CONTEXT.md`, your docs and plans, and decide for itself whether to build it. The playbook's Part D
section "The judgment call stays interactive, on purpose" says don't, and gives the reason by
reference: that "recreates the exact failure Part C already fixed once." `wayfinder`'s "ask the user
how to proceed" fallback had no one to answer it headless; "an unattended loop making its own
security/compliance judgment calls has no one to catch it when it's wrong, either."</p>

<p>The code agrees with the prose. `adw_watch.py`'s module docstring: "The judgment call — is this
issue feasible, compatible with what's already live, compliant, secure — is NOT this script's job.
It only ever claims issues already carrying `Status: ready-for-agent` ... This script trusts that
gate; it does not re-check it." `frontier()` filters on the status string and nothing else about
the ticket's content — the whole candidate filter is one line:</p>

```python
READY = "ready-for-agent"
...
candidates = [i for i in issues if i.status == READY and is_unblocked(i, groups[i.feature])]
```

<p>Scout and planner's Part C wiring (glossary/OKF/ast-grep discovery,
delta-scoping) still runs inside every dispatched chain underneath — the playbook calls that
"defense-in-depth, not a substitute for the triage gate."</p>

<Callout kind="why" label="Judgment once, by a human; only the result is consumed headless">
<p>This is the same shape as bootstrap vocabulary in Chapter 6. `grill-with-docs` runs the
  interview once, interactively, and writes the <em>result</em> into `CONTEXT.md` for every later
  run to read. `/triage` runs the feasibility/compliance judgment once, interactively, and writes
  the <em>result</em> — a durable agent brief plus `Status: ready-for-agent` — into the ticket for
  the watcher to consume. In neither case does the judgment process itself run headless; in both
  cases only its output does. The playbook states the parallel outright: "That's the same pattern
  as `grill-with-docs`."</p>
</Callout>

## What /triage actually does before it writes ready-for-agent

<p>The `triage` skill is not vendored in this repo — it lives in the same interactive-only table as
`grill-with-docs` in the playbook's cheat sheet, and both carry `disable-model-invocation: true`.
What the playbook records about it: it checks feasibility, redundancy against existing
implementation, `.out-of-scope/` for prior rejections, and compliance; it "waits for maintainer
direction at every step and never runs unattended"; and it owns five canonical states:</p>

<table>
  <tr><th>State</th><th>Meaning</th><th>Visible to the frontier scan?</th></tr>
  <tr><td>`needs-triage`</td><td>filed, not yet judged — where `/to-spec`/`/to-tickets` should leave things</td><td>no</td></tr>
  <tr><td>`needs-info`</td><td>judged, blocked on a question for a human</td><td>no</td></tr>
  <tr><td>`ready-for-agent`</td><td>approved; a durable agent brief has been posted</td><td><strong>yes</strong></td></tr>
  <tr><td>`ready-for-human`</td><td>needs a person — also where a failed dispatch lands</td><td>no</td></tr>
  <tr><td>`wontfix`</td><td>rejected or already exists</td><td>no</td></tr>
</table>

<p>Only one of those five strings makes a ticket claimable. Part D is explicit that its terminal
state for approved work "means a durable **agent brief** has been posted to the issue" — and on the
local-markdown tracker, posting that brief on a not-yet-tracked item is what creates
`issues/NN-slug.md` in the first place (the v4.5 correction in "Filing: less manual than it looks").
The ticket body, verbatim, is then the literal prompt the dispatched chain receives:
`utils.resolve_prompt(str(issue.path))` in `dispatch()`. Whatever `/triage` wrote into the file is
what the planner reads; nothing in between rewrites it.</p>

## The sharp edge: to-spec and to-tickets self-promote by default

<p>Here is where the gate leaks. Part D's "Filing" section: `/to-spec` and `/to-tickets` "both apply
the `ready-for-agent` triage label themselves by default (their own 'no need for additional triage'
/ 'the tickets are agent-grabbable by construction' instructions)." Inside the headless planner
that is overridden — Chapter 6's AFK bullet list forces both to file at `needs-triage` — but running
either skill <strong>by hand</strong> in your own harness gets their unmodified behavior. Two ways
that goes wrong, per the playbook:</p>

<ol class="steps">
  <li><p><strong>Bold lines, invisible ticket.</strong> `/to-tickets`' local-ticket-template writes
  `**Status:**`/`**Blocked by:**` in bold. The playbook (written against an earlier
  `STATUS_RE`) describes such a ticket as silently invisible to the queue — "a stall, not an
  error." The current `adw_watch.py` regex tolerates exactly that bold form —
  `STATUS_RE = re.compile(r"^\*{0,2}Status:\*{0,2}[ \t]*(\S+)", re.MULTILINE)`, `\*{0,2}` on both
  sides of the key, with a comment dating the fix to "four portfinder tickets" found live on
  2026-09-14 — so this specific stall is closed; the next lesson covers what the regex still
  rejects.</p></li>
  <li><p><strong>Plain lines, untriaged ticket.</strong> If you (or the model) write plain
  `Status: ready-for-agent` instead, you get exactly what the gate exists to prevent: "`just watch`
  will build it without anyone having judged feasibility, redundancy, or compliance first." The
  watcher cannot tell a self-promoted `ready-for-agent` from a triaged one — the string is the
  gate.</p></li>
</ol>

<Callout kind="trap" label="Before you commit a hand-run to-spec / to-tickets result">
<p>The playbook gives two acceptable exits. Either hand the output to `/triage` before committing,
  so the promotion happens through the gate; or hand-edit every `Status:` line to `needs-triage`
  and confirm the files use the canonical plain or bold `Status:`/`Blocked by:` shape — "same shape
  the Mandatory checkpoints below already check for." What you must not do is commit a
  `ready-for-agent` ticket nobody triaged and let the next `just watch --once` find it.</p>
</Callout>

## A ceiling to know about: triage can reach further than the watcher

<p>Current `triage` can also treat external pull requests as a request surface — "a PR is an issue
with attached code," same roles, same states — if the tracker config marks them in scope (off by
default). The playbook notes the ceiling: a PR only exists on a GitHub/GitLab tracker, and
`adw_watch.py`'s `main()` returns exit code `2` for anything `detect_tracker()` reports as
non-local. Triage can flip a PR to `ready-for-agent`; nothing will ever claim it until the
GitHub/GitLab support the watcher's own docstring flags as unbuilt actually lands. Sole promoter
means the gate is upstream of the queue — it does not mean everything it promotes has a queue
behind it yet.</p>


    <p>Nothing was claimed: `needs-triage` is well-formed and invisible. Now do the thing the
    lesson says not to do in real work — edit the one word to `Status: ready-for-agent`, commit,
    and run `just watch --once` again. The watcher claims it immediately and dispatches the full
    chain on a body nobody triaged. That is the sharp edge, reproduced: the watcher cannot tell
    your hand edit from a `/triage` promotion. Afterward, read the ticket's new `Status:` line
    (`resolved` or `ready-for-human`) and `git log --oneline -5` to see the claim and resolve
    commits, then delete `.scratch/gate-demo/` and commit the removal so the capstone starts clean.
    (If you'd rather not spend a full chain on a do-nothing ticket, stop after the first run — the
    `queue empty` at `needs-triage` is the half of the proof that costs nothing.)</p>
  </li>
</ol>
