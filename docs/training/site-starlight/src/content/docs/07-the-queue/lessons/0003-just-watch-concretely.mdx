## What just watch is

<p>`just watch` runs `adw_watch.py` — the headless half of the dark-factory queue. Its job,
stated in its own module docstring, is narrow on purpose: scan the issue tracker for
`ready-for-agent` work, claim the frontier, and dispatch it through the full SDLC chain
(`adw_simple_sdlc.py`: planner → builder → reviewer → revision loop → documenter → commit — not
the lighter `plan_build_test` chain `just sdlc` wraps, because an unattended dispatch has nothing
else independently checking it besides the test gate passing, so it gets the review/revision loop
a supervised manual run could otherwise skip).</p>

<Callout kind="trap" label="The judgment call is not this script's job">
<p>`adw_watch.py` only ever claims issues already carrying `Status: ready-for-agent` — a state that
  should only be reached by an interactive `/triage` session posting a durable agent brief. This
  script trusts that gate; it does not re-check feasibility, compatibility, or compliance itself.
  Chapter 7's "Triage as Sole Promoter" lesson covers why that judgment stays interactive; this
  lesson is about what happens strictly downstream of it.</p>
</Callout>

## The four stages

<p>One scan-claim-dispatch-resolve cycle, run by `run_once()`:</p>

<ol class="steps">
  <li><p><strong>Scan.</strong> `discover_issues()` walks every `.scratch/&lt;feature&gt;/issues/*.md`
  file and reads its `Status:` line. A file with no parseable `Status:` line at all is not a
  tracked issue and is skipped — but first, `_check_format()` checks whether it merely *looks*
  like one that's malformed, and if so, warns loudly rather than skipping silently (more on this
  below).</p></li>
  <li><p><strong>Frontier.</strong> `frontier()` filters to issues at `Status: ready-for-agent`
  whose every `Blocked by:` target already resolved, groups by feature (blocker numbers are only
  unique <em>within</em> one feature's `issues/` dir — a "01" in one feature never blocks against
  another feature's "01"), and picks the lowest `(feature, number)` first. Same "first by number
  wins" rule wayfinder itself uses — the whole function is quoted just below the list.</p></li>
  <li><p><strong>Claim.</strong> `set_status()` writes `Status: claimed` <em>before</em> touching
  anything else, and `commit_watcher_state()` commits that write immediately, so the claim itself
  survives even if everything after it crashes. This is not an explicit lock — there is no
  concurrency guard in the code itself — but scan-then-commit ordering means a second `just watch`
  invocation that runs its own scan after the first's commit lands will see the ticket already
  claimed. Two runs racing to scan at the exact same instant, before either commits, is a real gap
  this design does not close.</p></li>
  <li><p><strong>Dispatch → Resolve.</strong> `dispatch()` runs the full SDLC chain with the
  issue's own body as the prompt, then writes the terminal state — `resolved` on success,
  `ready-for-human` on failure — and commits that too.</p></li>
</ol>

<p>Frontier's whole function:</p>

```python
def frontier(issues: list[Issue]) -> Issue | None:
    groups = group_by_feature(issues)
    candidates = [i for i in issues if i.status == READY and is_unblocked(i, groups[i.feature])]
    if not candidates:
        return None
    candidates.sort(key=lambda i: (i.feature, i.number))
    return candidates[0]
```

## Reading Status: and Blocked by: — plain or bold, nothing else

<p>Two regexes decide what the whole queue can see:</p>

```python
STATUS_RE = re.compile(r"^\*{0,2}Status:\*{0,2}[ \t]*(\S+)", re.MULTILINE)
BLOCKED_BY_RE = re.compile(r"^\*{0,2}Blocked by:\*{0,2}[ \t]*(.+)$", re.MULTILINE)
```

<p>`\*{0,2}` tolerates exactly the two forms seen in the wild: plain `Status: X` (what this
script's own `set_status()` writes) and `**Status:** X` (what `to-tickets`' own
local-ticket-template uses, bold, per its `SKILL.md`). It does **not** tolerate anything else —
underscores, backticks, a missing colon, wrong casing — on purpose. Found live: four real tickets
filed entirely in bold by `to-tickets` were silently invisible to the frontier scan, and `just
watch --once` reported a clean "queue empty" with no error at all.</p>

<Callout kind="why" label="Fail loud, not silent — one level up">
<p>The fix was not just tolerating bold. `_check_format()` also runs a *near-miss* detector — a
  looser pattern that matches anything that looks like it's <em>trying</em> to declare
  `Status:`/`Blocked by:` but doesn't match either canonical form:</p>

```python
_STATUS_NEAR_MISS_RE = re.compile(r"^[*_\s]{0,3}status", re.MULTILINE | re.IGNORECASE)
_BLOCKED_BY_NEAR_MISS_RE = re.compile(r"^[*_\s]{0,3}blocked\s+by", re.MULTILINE | re.IGNORECASE)

def _check_format(text: str, path: Path) -> None:
    if _STATUS_NEAR_MISS_RE.search(text) and not STATUS_RE.search(text):
        print(f"just watch: WARNING -- {path} has a Status:-like line that "
              "doesn't match the canonical 'Status: X' or '**Status:** X' "
              "form. This ticket is INVISIBLE to the frontier scan until "
              "fixed.", file=sys.stderr)
    if _BLOCKED_BY_NEAR_MISS_RE.search(text) and not BLOCKED_BY_RE.search(text):
        print(f"just watch: WARNING -- {path} has a Blocked by:-like line "
              "that doesn't match the canonical 'Blocked by: NN' or "
              "'**Blocked by:** NN' form. Blocking will not be honored for "
              "this ticket.", file=sys.stderr)
```

<p>`[*_\s]{0,3}` rather than `\W*` is deliberate: `\W` excludes underscore (a word character
  in Python's `re`), so a `\W*`-based detector let `_Status_:` through undetected. No trailing
  `\b` for the same reason. The one known gap, per the comment above the regex: a
  backtick-wrapped `` `Status:` `` matches neither the strict nor the near-miss pattern, so that
  one form is still a silent skip. If the near-miss fires without the strict regex also matching,
  the script prints a loud warning naming the exact file. One malformed ticket must never take the whole
  queue down — the detector never raises — but it must also never again fail invisibly. That was
  the actual bug: not that bold tickets are rejected (correct behavior, tickets need a canonical
  form) but that rejection produced no signal at all.</p>
</Callout>

## Blocked by: parsing is stricter than it looks

<p>`read_blocked_by()` strips every `(explanatory parenthetical)` from the whole value
<strong>first</strong>, then splits on commas, trims trailing `.;:,` from each token, drops
empty tokens and anything matching `_NONE_RE = re.compile(r"^none\b|^n/a\b", re.IGNORECASE)`
("no blocker" — same effect as omitting the line), and keeps everything else. A kept token that
does not match `_TICKET_NUMBER_RE = re.compile(r"^\d+$")` is still kept as a blocker (the safe
default: never silently unblock something that might genuinely be blocked) but prints a warning
that it will never resolve, so the ticket is stuck at `ready-for-agent` forever until the line is
fixed. The order — parenthetical first, comma-split second — is the one line that matters:</p>

```python
value = re.sub(r"\s*\([^)]*\)", "", m.group(1))
tokens = (b.strip() for b in value.split(","))
```

<Callout kind="trap" label="Prose in Blocked by: still stalls — parentheticals no longer do">
<p>Two shapes used to stall a ticket silently and are now handled: `Blocked by: None (port_directory
  tables ship; this only reads them).` and `Blocked by: none (API exists, see spec.md)` — the
  second with a comma <em>inside</em> the parenthetical, which an earlier version comma-split
  before stripping. Both now resolve to no blockers (the previous lesson's `[run]` step proves
  it). What still stalls: a value that survives the strip and is neither `none`/`n/a` nor a bare
  number — `Blocked by: the port-listing ticket`, say. That token is kept, `is_unblocked()` returns
  `False`, and the ticket sits at `ready-for-agent`, passing every mandatory checkpoint from the
  previous lesson, invisible to the frontier — with the one stderr warning above as the only
  signal. <strong>If a ticket has no real blocker, omit the `Blocked by:` line entirely; if it has
  one, write the bare number.</strong></p>
</Callout>

## What happens on success versus failure

<p>`dispatch()`'s outcome handling, quoted with only the explanatory comments removed
(`FAILED_STATE = "ready-for-human"`, `RESOLVED = "resolved"`):</p>

```python
def dispatch(issue: Issue, config: str) -> tuple[bool, str]:
    set_status(issue.path, CLAIMED)
    commit_watcher_state(f"just watch: claim {issue.path}")

    adw_id = utils.new_id()
    prompt = utils.resolve_prompt(str(issue.path))
    try:
        exit_code = adw_simple_sdlc.main(prompt, config=config, adw_id=adw_id)
    except (Exception, SystemExit) as exc:
        set_status(issue.path, FAILED_STATE)
        append_comment(issue.path, f"> *just watch: session `{adw_id}` crashed: {exc}*")
        commit_watcher_state(f"just watch: session {adw_id} crashed -- flipped to ready-for-human")
        return False, adw_id

    if exit_code == 0:
        set_status(issue.path, RESOLVED)
        append_comment(issue.path, f"> *just watch: resolved by session `{adw_id}`.*")
        commit_watcher_state(f"just watch: resolve {issue.path} (session {adw_id})")
        return True, adw_id

    set_status(issue.path, FAILED_STATE)
    append_comment(
        issue.path,
        f"> *just watch: session `{adw_id}` failed (exit {exit_code}). "
        f"Flipped to ready-for-human -- see `just phases {adw_id}` for what broke.*",
    )
    commit_watcher_state(f"just watch: session {adw_id} failed -- flipped to ready-for-human")
    return False, adw_id
```

<p>Three outcomes, two of them both land on `ready-for-human`: a crash inside the chain, and a
clean-but-nonzero exit from it. Neither is ever retried silently — "a loop that keeps
re-attempting the same failure burns money without anyone finding out until later," per the
adoption playbook's own reasoning for this design (Part D, "What `just watch` does, concretely").
Every path also appends a comment naming the session id, so `just phases &lt;adw_id&gt;` can always
tell you exactly what broke.</p>

<Callout kind="trap" label="except (Exception, SystemExit) — not just Exception">
<p>`agents.validate()` raises `SystemExit` on a config problem — a bad model string, a missing
  prompt file. `SystemExit` inherits `BaseException`, not `Exception`, so a bare `except
  Exception:` never catches it. Found live against a real malformed model string: the config
  error crashed the entire watcher process, skipping this handler completely and leaving the issue
  stuck at `Status: claimed` forever, with no resolution commit. `KeyboardInterrupt` — also a
  `BaseException` — is deliberately left uncaught here, so an operator's Ctrl+C still stops the
  watcher, which is the behavior they actually want.</p>
</Callout>

## Claiming commits — and refuses to run against a dirty tree

<p>Every status write is committed immediately, because the ADW's own commit phase fires
mid-run, before this script's final write — without `commit_watcher_state()`, the last status
transition would sit uncommitted after every single run. That has a consequence at the very start
of the cycle: `run_once()` refuses to claim anything if the working tree is already dirty, because
claiming commits, and an unrelated in-progress change sitting there would get swept into that
commit by the same `git add -A` reach every ADW commit phase already has.</p>

```python
if git_helper.is_repo() and git_helper.is_dirty():
    print("just watch: working tree is dirty -- refusing to claim anything "
          "until it's clean (claiming commits, and would sweep in whatever "
          "else is sitting there)")
    return False
```

## Exit codes, and why --once is the shape that composes

<p>`main()` returns `0` if work was found and dispatched (regardless of outcome — check the
issue's new `Status:` to know which), `1` if the queue was empty, `2` if the tracker isn't
local-markdown (a GitHub or GitLab tracker is detected and refused with a clear error, not
silently treated as empty — that wiring does not exist yet). `--once` runs exactly one cycle and
exits with that code, which is the right shape for `cron`/`launchd` to call on an interval — the
watcher itself stays a script you can run once, not a daemon SSSF grows on your behalf. Without
`--once`, it loops on `--interval` seconds instead. The tracker check runs <em>before</em> the
dirty-tree check, and reads exactly one line:</p>

```python
def detect_tracker(root: Path) -> str:
    doc = root / "docs" / "agents" / "issue-tracker.md"
    if doc.is_file():
        text = doc.read_text()
        first_line = text.splitlines()[0] if text.strip() else ""
        if "GitHub" in first_line:
            return "github"
        if "GitLab" in first_line:
            return "gitlab"
        if "Local Markdown" in first_line:
            return "local"
    return "local" if (root / ".scratch").is_dir() else "unknown"

def main(scratch_dir: str, config: str, once: bool, interval: int) -> int:
    root = Path.cwd()
    tracker = detect_tracker(root)
    if tracker != "local":
        print(f"just watch: {tracker} issue tracker detected -- not implemented yet. ...",
              file=sys.stderr)
        return 2
    path = Path(scratch_dir)
    if once:
        return 0 if run_once(path, config) else 1
    while True:
        run_once(path, config)
        time.sleep(interval)
```
