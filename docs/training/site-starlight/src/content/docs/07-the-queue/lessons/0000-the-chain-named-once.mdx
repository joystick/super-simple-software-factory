<Callout kind="win" label="The win">
<p>You can recite the dark-factory chain in order, say which steps a human runs interactively and
  which one runs headless, name the single state (`ready-for-agent`) that hands work from one half
  to the other, and explain why the queue always dispatches the full SDLC chain rather than the
  lighter one `just sdlc` wraps.</p>
</Callout>

<p>The full dark-factory chain is five steps, named once so every later lesson in this chapter can point back to a single ordered list instead of re-deriving it: `/grill-with-docs` (interactive, commits `CONTEXT.md`/`docs/adr/`), `/to-spec` (synthesizes the spec), `/to-tickets` (slices it into tickets), `/triage` (the only thing allowed to promote a ticket to `ready-for-agent`), and `just watch` (the headless scan-claim-dispatch-resolve loop covered in this chapter's `just watch` lesson). This lesson introduces the chain end to end before the following lessons go deep on any one link — commit the checkpoints and the mandatory-checks step between (4) and (6), covered next.</p>

## The list, exactly as the playbook writes it

<p>Part D of the adoption playbook opens with a section literally titled "The whole chain, named
once." It is six numbered lines, and this chapter's structure follows them one to one:</p>

<table>
  <tr><th>#</th><th>Step</th><th>Who runs it</th><th>Leaves behind</th><th>Lesson</th></tr>
  <tr><td>1</td><td>`/grill-with-docs`</td><td>you, interactively</td><td>committed `CONTEXT.md`/`docs/adr/`</td><td>Chapter 6, "Bootstrap Vocabulary"</td></tr>
  <tr><td>2</td><td>`/to-spec`</td><td>you or the planner</td><td>`.scratch/&lt;feature&gt;/spec.md`</td><td>this lesson</td></tr>
  <tr><td>3</td><td>`/to-tickets`</td><td>you or the planner</td><td>`.scratch/&lt;feature&gt;/issues/NN-slug.md`, one per phase</td><td>this lesson</td></tr>
  <tr><td>4</td><td>`/triage`</td><td>you, interactively</td><td>a ticket at `Status: ready-for-agent` carrying an agent brief</td><td>"Triage as Sole Promoter"</td></tr>
  <tr><td>5</td><td>Commit; run the mandatory checkpoints</td><td>you</td><td>a clean tree the queue can actually see</td><td>"Filing Checkpoints"</td></tr>
  <tr><td>6</td><td>`just watch`</td><td>headless</td><td>`resolved` or `ready-for-human`, plus a commit</td><td>"just watch, Concretely"</td></tr>
</table>

<p>Steps 1 and 4 are the two places a human's judgment is required; steps 2 and 3 produce
artifacts; step 5 is verification; step 6 is the only unattended step. The playbook's Part D
mermaid diagram draws the same shape with two nodes highlighted: the filing hand-off into
`/triage`, and the `ready-for-agent` state itself — the two points where a human decision becomes
something a headless loop is allowed to consume.</p>

<Callout kind="why" label="Why name it once">
<p>Every later lesson in this chapter points at a step by number or by name and never re-explains
  the order. That is deliberate: the playbook's own reasoning for the queue is "don't build a new
  work-item format" — reuse wayfinder's map/child/frontier/claim/resolve vocabulary verbatim. The
  training mirrors that discipline. One list, one order, one set of names; if you find yourself
  wondering "which chain does the queue run" or "who promotes a ticket," the answer is always in
  this table, not in a per-ticket decision.</p>
</Callout>

## Interactive on the left, headless on the right

<p>The chain has a seam down the middle. Everything up to and including `/triage` runs in your own
harness with you present; everything from `just watch` onward runs with nobody present. The reference
glossary's Dark-factory entry (`docs/reference/the-queue/Dark-factory.md`) makes the same cut from the
skill side: five skills are vendored onto agent roles and run headless (`wayfinder`, `to-spec`,
`to-tickets`, `tdd` on the planner; `code-review` on the reviewer), and two are deliberately
<em>not</em> vendored — `grill-with-docs` and `triage` — because they only ever run interactively.
Both carry `disable-model-invocation: true` for that reason.</p>

<p>The seam is a single string in a single file. `adw_watch.py`'s module docstring says it only ever
claims issues "already carrying `Status: ready-for-agent`, a state that should only be reached by an
interactive triage session ... posting a durable agent brief. This script trusts that gate; it does
not re-check it." Two vocabularies meet at that line on purpose: `triage`'s five canonical states
(`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`) get an issue
<em>to</em> `ready-for-agent`; the watcher then layers wayfinder's own `claimed`/`resolved` on top to
track its own work, and a failed run flips back to `ready-for-human` — a triage state — so a person
sees it.</p>

## Which chain the queue runs, and why it is never the lighter one

<p>Step 6 always dispatches `adw_simple_sdlc.py` — planner → builder → reviewer → revision loop →
documenter → commit. The docstring gives the reason in one sentence: "an unattended queue dispatch
gets no other independent check besides the test gate, so it needs the review/revision loop a
supervised manual run could otherwise skip." When you run `just sdlc` by hand you can eyeball the
plan before anything ships; nothing eyeballs a `just watch` dispatch, so the queue pays for the
review loop every time.</p>

```text
$ just watch --once
just watch: claiming .scratch/portfinder/issues/01-list-ports.md
just watch: committed watcher state (a1b2c3d): just watch: claim .scratch/portfinder/issues/01-list-ports.md
... adw_simple_sdlc runs: planner -> builder -> reviewer -> revision loop -> documenter -> commit ...
just watch: committed watcher state (e4f5a6b): just watch: resolve .scratch/portfinder/issues/01-list-ports.md (session 8f2c1a9e)
just watch: session 8f2c1a9e succeeded -- .scratch/portfinder/issues/01-list-ports.md
```

<p>The shape of those lines is what the rest of this chapter teaches you to read: a claim commit
before any work, the full chain in the middle, a resolve (or fail) commit after. The `justfile`'s
`watch` recipe is one line, so every flag the script accepts passes straight through:</p>

```makefile
# dark-factory queue: claim the next ready-for-agent issue and run sdlc on it.
# Only ever claims work already triaged to ready-for-agent -- see the
# adoption playbook's Part D. --once for cron/launchd; omit for a standing
# loop: just watch --interval 300
watch *ARGS:
    uv run adws/adw_watch.py --config {{config}} "$@"
```

<p>And the flags the script itself declares, from its `argparse` block: `--config` (default
`adws/adw_sssf_config/sssf.config.yaml`), `--scratch-dir` (default `.scratch`), `--once` ("one
scan-claim-dispatch-resolve cycle, then exit (0 dispatched, 1 empty queue, 2 unsupported tracker)
— the right mode for cron/launchd"), and `--interval` (seconds between scans when not `--once`,
default `300`).</p>

## The one manual hand-off in the chain

<Callout kind="trap" label="grill ends at CONTEXT.md, not at a ticket">
<p>Step 1 does not feed step 4 on its own. `/grill-with-docs` ends at a committed
  `CONTEXT.md`/`docs/adr/` update and "does not hand `/triage` anything" — Part C's "The grill →
  triage handoff is manual, on purpose" section records this as an accepted decision, not a gap
  to close: a wrapper skill was evaluated and deliberately not built. The guard is a checklist
  line in Part C's definition of done: if a grilling session ran, run `/triage` before leaving the
  session. A settled-but-unfiled grill is invisible to the queue, and nothing lists "settled but
  unfiled" work.</p>
</Callout>
