Wiring and writing gates

Two different acts, and two different families of gate. Lesson 1 covered half of one of them.

The win

You can wire a quality block to a real command, and write a gate function from scratch. By the end you will have written one that fails a run whose own quality blocks are still placeholders — a gate that checks your gates.

Why the second family exists

An agent's envelope is a set of claims: status success, summary "added the endpoint", artifacts ["specs/plan.md"]. Nothing about producing that JSON requires any of it to be true.

Envelope gates are "agent proposes, code disposes" applied to the report rather than the code. They check what is mechanically checkable — did the file appear, is it non-empty, does the diff contain what was claimed. Whether the plan is any good is a reviewer's job, not a gate's.

Part 1 — wiring a quality block

Open adw_modules/quality.py. Each block is a function returning a QualityCheckSpec. Wiring one means replacing the placeholder argv:

def test(run) -> QualityCheckResult:
    return _run(QualityCheckSpec(
        name="test",
        area="backend",
        operation="build",
        argv=["deno", "test", "--doc"],     # <- the whole job
        timeout_seconds=600,
    ), run)

Four rules, each earned the hard way

  1. argv is a list, never a shell string. A list means no shell — so no pipe can replace your exit code. deno test | tee log is a gate that can never fail, because tee succeeds.

  2. Call binaries by bare name. These run with the operator's environment, so deno resolves the way it does in your terminal. An absolute path bakes your machine into the trace.

  3. Scope lives in the config file, not the argv. Put includes in deno.json or pyproject.toml. Then the gate and your local run cannot disagree — which is the whole reason to have a gate.

  4. Delete blocks you do not have. Remove them from the list in run_quality() too. A block running echo reports a check that never happened.

Then verify — lesson 1's procedure

Wiring is not finishing. Introduce a defect of the class that tool catches, confirm that gate goes red and the others stay green, restore. A wired gate you have not watched fail is still not a gate.

Part 2 — writing an envelope gate

The whole contract is one line:

def my_gate(envelope: EnvelopeBase, run) -> GateReport

Build a GateReport by calling report.check(item, ok, note) once per thing you looked at. Violations are derived from the failed checks — you never build them yourself.

def artifacts_exist(envelope: EnvelopeBase, run) -> GateReport:
    report = GateReport()
    for a in envelope.artifacts:
        p = Path(a)
        report.check(a, p.exists(),
                     f"exists, {_size(p)}" if p.exists()
                     else "declared artifact does not exist")
    return report

A gate is a loop and a return. That is the entire pattern.

Why one check per item

Every check is recorded whether it passed or failed, so a green gate says what it verified, not merely that it passed:

OK    justfile          exists, 4.4KB
FAIL  specs/ghost.md    declared artifact does not exist

Compare with a gate that returns a bare boolean. Green would tell you nothing — the exact problem from lesson 1, reproduced one level up.

The note is the message the agent receives

On a failed check, note becomes the violation text, and violations are sent back into the same agent session as a correction — bounded by the phase's retries. Write notes for the agent that must act on them:

PoorGood
"failed""declared artifact does not exist"
"bad diff""claimed changed but not in the diff"
