A gate you have not watched fail

Why a green result carries almost no information, and the three-minute procedure that turns it into evidence.

The win

You can look at any factory — yours or a colleague's — and say precisely what its green banner does and does not establish. And you can settle the question in about three minutes per gate.

What a gate is

A gate is a deterministic check that decides whether an agent's work is acceptable. Three properties, and none of them is clever:

  1. Code runs it, not a model. No LLM is asked "did the tests pass?" A subprocess runs a command and reads the exit code.
  2. It judges the result, not the claim. The agent says "I added the feature and tests pass." The gate ignores that sentence and runs the suite.
  3. Its verdict is an exit code. 0 passes. Anything else fails.

That is the entire mechanism. The lack of cleverness is the point: a verdict you cannot argue with.

The problem

A gate's substance is the command it runs. And:

echo "PLACEHOLDER"   →  exit 0
deno test            →  exit 0     (when the suite genuinely passes)
The core idea, and everything else follows from it

A gate has two states that are identical from the outside: it checked something and found nothing wrong, or it is incapable of finding anything wrong.

A green result does not distinguish them. Neither does the trace. Neither does reading the config, as we will see.

Executed on a repo containing one file and no tooling whatsoever:

$ uv run adws/adw_quality.py "is this repo healthy?"

  quality test:      passed (exit 0)   ← ran: echo 'PLACEHOLDER test…'
  quality lint:      passed (exit 0)   ← ran: echo 'PLACEHOLDER lint…'
  quality typecheck: passed (exit 0)   ← ran: echo 'PLACEHOLDER typecheck…'
  quality build:     passed (exit 0)   ← ran: echo 'PLACEHOLDER build…'
  checks: 4/4        status ✓ success

No test suite. No linter. No typechecker. Four echo statements and a green banner.

Reading the command is not enough either

The obvious defence is to inspect what each gate runs. Necessary, and insufficient — a real tool with a real command can also check nothing:

$ deno test --filter "smoke"
ok | 0 passed | 0 failed | 66 filtered out     exit 0

$ deno test
ok | 66 passed | 0 failed                      exit 0

No placeholder anywhere. A real runner, a plausible command, exit 0, zero tests executed. A filter that matches nothing, a path that points at the wrong directory, a suite scoped to a folder someone renamed — each produces this.

The only thing that settles it

For each gate G, separately:

  1. Introduce a defect of the class that tool exists to catch.

  2. Run every gate.

  3. Require both: G goes red, and every other gate stays green.

  4. Restore.

The second half of step 3 is the half people drop, and it is the half that isolates. Red-on-G alone cannot distinguish "lint caught my unused import" from "everything is red because I broke the build".

Choosing the probe

A probe aimed at the wrong tool produces a false diagnosis — the gate stays green, and you conclude it is broken when it is healthy. Measured:

Reading the result

OutcomeDiagnosis
G stays greenThe gate does not reach that defect. Fix the gate — or if G is a test suite, suspect the test.
Everything goes redThe probe was not specific. Choose a narrower one.
One other gate also goes redA real overlap, or the wrong probe. Overlaps exist — deno test type-checks, so a type error trips both test and check. Know your overlaps; do not accept surprises.

Why per gate, and not "the build went red"

A dead lint gate and a real bug, run together:

bug present   test: failed   lint: passed   typecheck: passed   →  2/3  RED
bug fixed     test: passed   lint: passed   typecheck: passed   →  3/3  GREEN

The build went red. A team that stops there concludes all three gates work. One is an echo. Once the bug is fixed, that dead gate is indistinguishable from a healthy one.

Breaking one thing proves at least one gate noticed. It never says which, and says nothing about the others.

A dead gate is worse than no gate

SSSF's fix loop hands a failing gate's verbatim output back to the builder to repair, then re-runs the gate. So when the test gate is an echo:

build    the builder writes broken code
test     echo → exit 0 → PASSED
         ↓  the fix loop NEVER FIRES — there is no failure to feed it,
            and the builder is never told anything is wrong
commit   "land the code only after the suite came back green" — it did
trace    status ✓ success · phases 5/5 passed

The bug is committed and the permanent record says the run succeeded. Nobody lied; every component did its job correctly. A dead gate does not merely fail to catch bugs — it disables the repair machinery and then certifies the result.

What SSSF actually gives you

One sentence

SSSF guarantees that an agent's claims are replaced by a deterministic verdict before work proceeds. Agent proposes, code disposes.

Everything else — roster, envelopes, trace, fix loop, permissions — serves that one guarantee. Its entire strength is the gates. A factory is exactly as trustworthy as its weakest gate, and a gate's trustworthiness cannot be read, only demonstrated.
