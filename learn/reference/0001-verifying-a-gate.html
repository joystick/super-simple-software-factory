Verifying a gate

Three minutes per gate. There is no substitute.

The rule

Say it out loud before you trust a green build

A gate you have not watched fail is not a gate.

Checking and being-incapable-of-checking look identical from outside. Only a deliberate defect separates them.

The procedure

For each gate, separately:

  1. Introduce a defect of the class that tool exists to catch.
  2. Run every gate.
  3. Require: that gate red, all others green.
  4. Restore. Confirm all green again.

Choosing the probe

ToolJobProbe
formatterlayout, whitespacenone — never gate on it
linterdead code, unused namesan unused import
type checkertypesa wrong annotation
testswrong behaviourchange a value an assertion reads
buildit compiles / bundlesa syntax error in an entry point

A wrong probe yields a false diagnosis: the gate stays green and you conclude it is dead when it is healthy.

Reading the outcome

ResultMeansDo
target red, rest greenthe gate is realrestore, next gate
target greendoes not reach that defectfix the gate; if it is a suite, suspect the test
everything redprobe too broadchoose a narrower defect
another gate red toooverlap, or wrong probeknow your overlaps; verify it is expected

Known overlap: deno test type-checks, so a type error trips both test and check. pytest and mypy are independent — a bad annotation leaves pytest green.

Wiring hazards

HazardWhy it kills a gate
cmd | tee logthe pipe replaces the exit code with the last command's; tee almost always succeeds
shell string instead of an argv listadmits pipes, redirection and quoting bugs — use a list, no shell
a filter matching nothingdeno test --filter smoke → exit 0, zero tests run
scoped at the wrong directorylints or tests a folder that has since been renamed
scope written in the argvthe gate and your local run drift apart — put scope in pyproject.toml / deno.json
an echo placeholdera freshly stamped factory ships every block this way
gating on a formatterauto-fixable, so it turns a fix into a failure and trains people to ignore red

Why "the build went red" is not enough

bug present   test: FAILED   lint: passed   typecheck: passed   →  2/3  RED
bug fixed     test: passed   lint: passed   typecheck: passed   →  3/3  GREEN
                             └── this gate is an echo, in both rows

A red build proves at least one gate noticed. Never which, never the others.

What a dead gate costs you

build    broken code written
test     echo → 0 → PASSED
         ↓  fix loop never fires: no failure exists to feed it
commit    green, so it commits
trace     status ✓ success · phases 5/5

It disables the repair machinery, then certifies the result. Worse than no factory, because the trace now looks like evidence.

The one-line summary of SSSF

An agent's claims are replaced by a deterministic verdict before work proceeds. Everything else serves that. The factory is exactly as trustworthy as its weakest gate.
