Prompting just sdlc

What to write, what not to bother writing, and the order to do it in.

Before any of this

Gates wired, and each one watched failing. A prompt cannot make a factory careful. Behind an unverified gate, a good prompt just produces unchecked work faster.

The division of labour

The promptThe gates
states intent — what you want to existenforce the standard — whether it holds up

This is why "write clean, correct code with good test coverage" is wasted words. Nothing checks it, so nothing enforces it. Say what you want built; let the gates say whether it is acceptable.

Anatomy

Six parts. Not all are needed every time; parts 1, 2 and 6 nearly always are.

#PartExample, from a real run
1Outcome"Add a savings_percent property to Receipt"
2Behaviour pinned"the total discount as a percentage of the subtotal, rounded to one decimal place, returning 0.0 when the subtotal is zero"
3Reach, if it spans things"everywhere a percent is currently accepted: MemberDiscount, BulkDiscount, CouponDiscount and the tax_percent argument"
4Convention anchor"follows the existing conventions (integer cents, applies to the subtotal, validated percent)"
5What to test"Add tests covering a matching code, a non-matching code, no code, and an invalid percent"
6Protection clause"Do not modify or delete any existing test"
Why part 6 is not optional

The builder has unrestricted write access. When a test blocks it, deleting an assertion is the cheapest path to green. It did not take that path in any run here — but that is virtue you have not constrained, and virtue is not a gate.

For a refactor, the stronger form: "No behaviour change: every existing test must pass unchanged."

Four prompts that worked

just sdlc "Add a savings_percent property to Receipt: the total discount as a
percentage of the subtotal, rounded to one decimal place, returning 0.0 when the
subtotal is zero. Add tests for it. Do not modify or delete any existing test."
                                                              → 7/7 phases, $0.48
just sdlc "Add coupon code support to the pricing engine: a CouponDiscount rule
that takes a code and a percent, applies only when that exact code is passed to
price_cart, and follows the existing conventions (integer cents, applies to the
subtotal, validated percent). Add tests covering a matching code, a non-matching
code, no code, and an invalid percent. Do not change existing behaviour."
                                                              → 5/5 phases, $0.61

Two more ran at $0.76 and $1.14. The $1.14 used a byte-identical prompt to the $0.61 run — the difference was the planner model, not the wording. Cost tracks model choice far more than prompt length.

Not worth writing

Don'tBecause
"write clean, maintainable code"not checkable, so nothing enforces it
"be careful" / "make sure it's correct"same — the gates decide this
"improve the pricing engine"no outcome to plan against; you will get something arbitrary
"edit pricing.py, add a class called X with methods Y and Z"you have written the plan yourself — if you want that, say so, but then the planner is wasted spend
a request needing three planskeep it to what one plan can express; feed slices one at a time

The order to work in

  1. Clean tree. git status. The commit phase runs git add -A and stages everything — unrelated work in progress lands in the agent's commit.

  2. Branch you are willing to throw away.

  3. just plan "…" first for anything architectural. The planner alone costs tens of cents. Read specs/<adw_id>_*.md — this is the cheap checkpoint where you find out it misread your architecture, instead of paying for a plan and a bad diff.

  4. just sdlc "…" once the plan reads right.

  5. Read the diff, not the banner. Green means the gates you verified found nothing wrong. That is all it has ever meant.

Long prompts

The positional argument accepts inline text or a path to a prompt file:

just sdlc specs/next-feature.md

Better for anything you want to revise, review or reuse — and it puts the request under version control alongside the work it produced.
